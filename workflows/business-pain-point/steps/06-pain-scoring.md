# 步骤 06 · 痛点评分排序与核心痛点确认

承接步骤 05 的候选痛点清单，本步骤先用**四维加权评分**给候选痛点排序，再用**硬门槛校验**锁定本轮主攻的「核心痛点池」。本步合并了原「痛点评分排序」与「核心痛点确认」两步——评分排名定优先级，硬门槛定取舍，不做二次主观筛选。

判定标准（评分公式、四维评分标准、核心痛点硬门槛、示例与模板）见 [../standards/06-pain-scoring-guide.md](../standards/06-pain-scoring-guide.md)。本文件只讲「在工作流里怎么执行这一步」。

## 执行流程与硬门槛闸门

Agent 必须严格按顺序执行以下 6 步：

```
Task Progress:
<!-- @AI_GENERATED -->
- [ ] 1. 清单读取：遍历步骤 05 精修后的全部痛点（按「代号（中文名）」引用 03 `pain_library`，含 outcome_type / affected_factors）。**本步打业务优先级分，与 03 痛点根因权重不同，不可混用。**
<!-- @AI_GENERATED: end -->
- [ ] 2. 四维打分：对每条痛点按 10/8/6/4/2 五档打【当前价值贡献 / 趋势压力 / 可解决性 / 可验证性】（价值贡献覆盖七类经营结果）。
- [ ] 3. 加权排序：按 40/25/20/15 求加权总分（满分10），从高到低排序。
- [ ] 4. ⛔ 硬门槛过滤 (Gate)：可解决性≥6（否则出局）；可验证性≥6（否则降级为战略/背景痛点，不进核心池）；必须能落到至少一个具体业务情境/作业环节。
- [ ] 5. 锁定核心池：原则上取加权总分前 3-5 且过门槛的痛点为核心痛点；其余按规则标注（战略·背景痛点 / 暂不纳入）。
- [ ] 6. 渲染输出：生成评分排序表 + 核心痛点池 Markdown，并写 yaml。
```

**注意**：核心池由评分排名 + 硬门槛共同决定，**不允许在过门槛后再凭主观偏好增删**核心痛点。

## 用户检查点 ★ (本步骤结束前的必须动作)

> ⛔ 硬闸门：本检查点为交付红线级约束，执行契约（五环节 / STOP 模板 / 恢复口令 / 批量跳过）以 [../standards/checkpoint-protocol.md](../standards/checkpoint-protocol.md) 为准。

在输出评分表与核心痛点池后，Agent **必须停止、等待用户确认**，未获用户确认**不得写入下一步文件**（禁止自问自答）。停止时按 STOP 模板抛出以下确认话术：
<!-- @AI_GENERATED: end -->


> “这是基于四维加权对候选痛点的评分排序，以及据此锁定的核心痛点池。请您确认：
> 1. 各痛点的四维打分是否符合贵司实际（尤其‘价值贡献’与‘可解决性’）？
> 2. 进入核心池的 3-5 个痛点，是否就是本轮最该优先攻坚的？被降级为‘战略/背景痛点’的是否认可？
>
> 如需调整打分或口径请指出；确认无误后，我们将进入步骤 07（大痛点组合）。”

**注意**：在用户明确回复“确认”或给出修改意见之前，流程强制暂停，不允许自行进入下一步。

## 单 agent / 多 agent 两种跑法

- **单 agent（基线，全平台可跑）**：当前 agent 顺序走完 6 步，过硬门槛，写 yaml + md，呈现检查点。
- **多 agent（探测到能力时）**：PL 派一个「Scoring Analyst」按四维独立打分并加权排序；Partner 复核打分一致性与硬门槛（重点核可解决性/可验证性是否被高估）。协调统一经 PL（hub-and-spoke），不依赖队友互发消息。

## 与上下游的衔接

- **上游**：步 05 提供经因果加工、可溯源的候选痛点清单。
- **下游**：步 07 **大痛点组合**——把核心痛点池中相互关联的痛点聚合为更具规模与说服力的「大痛点」。（注：关键场景识别在第 8 步、价值量化在第 9 步、实施路径在第 10 步；本步只排序与锁池，不做场景立项。）
