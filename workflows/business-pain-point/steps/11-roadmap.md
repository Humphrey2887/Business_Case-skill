# 步骤 11 · 实施路径（可选收尾步）

> **本步可选**：当 Business Case 需要落地路线图时执行；纯诊断或仅做价值论证可跳过，直接进入交付。

承接步骤 09 的价值量化与步骤 10 的技术架构（Ontology），本步骤把关键场景按"价值 × 数据就绪"排成实施波次，编排进**固定四阶段**标准路线，并按用户启动时间换算为**绝对日期**；技术架构中的 agent / agent skill / 数据接入即为可被排入各阶段的**建设对象**。本步从"分析"转入"交付编排"，可以、且需要谈数据底座/本体/智能体等建设动作（不再受前序反"缺系统"红线约束）。

判定标准（定义、四阶段模型、优先级 2×2、时间编排、建设边界、PPT 映射示例、标准话术、输出模板）见 [../standards/11-roadmap-guide.md](../standards/11-roadmap-guide.md)。本文件只讲「在工作流里怎么执行这一步」。

## 输入

- `process/10-ontology.yaml`（步 10 技术架构：`agents[]`、`agent_skills[]`、`data_sources[]` 及其 `linked_scenarios`，作为四阶段建设波次的**建设对象**来源）

## 输出

- `process/11-roadmap.yaml` — 结构化波次 + 四阶段编排 + 边界（模板见 [../templates/yaml-formats.md](../templates/yaml-formats.md)）
- `11-roadmap.md` — 可读文档，使用 guide 第 8 节输出模板

## 执行流程与时间闸门

Agent 必须严格按顺序执行（对齐 guide 第 3/4 节）：

```
Task Progress:
- [ ] 1. 读取场景与技术架构：取步骤 09 的价值量级 + 步骤 08 的 value_status/feasibility + 步骤 08 排除项里的前置条件 + 步骤 10 技术架构的 agent / agent skill / 数据接入（作为建设对象）。
- [ ] 2. ⛔ 取启动时间 (Gate)：取用户的 T0 与硬截止、组织层级；缺 T0 则在检查点向用户索要，不得臆造正式排期（试跑可假设并显式标注）。
- [ ] 3. 波次排序：价值量级 × 数据就绪 做 2×2，定 wave1/2/3；缺数据底座的高价值场景不得排进首批波次；技术架构中的 agent / agent skill / 数据接入作为可被排入各波次的建设对象。
- [ ] 4. 映射四阶段：把波次与前置条件塞进固定四阶段（前置数据→阶段2，首批 Quick Win→阶段3，深化/复制→阶段4，投融资/边界→阶段1-2 gating）。
- [ ] 5. 算绝对日期：按各阶段标准周期从 T0 累加成绝对日期区间；节奏按集团级(年度)/单场景(季度)取档。
- [ ] 6. 定里程碑/交付物/边界/依赖风险：划清总部统建/区域适配/现场执行；列依赖与风险及缓解。
- [ ] 7. 写 yaml + md，并显式标出"阶段2 回填第9步待确认 baseline → 潜在池价值升入总额"的闭环。
```
<!-- @AI_GENERATED: end -->

> 阶段数量固定为 4，不随 `--length` 变化；`--length` 只影响每阶段铺开的场景数量与文档详略。

## 用户检查点 ★ (终步，本步骤结束前的必须动作)

> ⛔ 硬闸门：本检查点为交付红线级约束，执行契约（五环节 / STOP 模板 / 恢复口令 / 批量跳过）以 [../standards/checkpoint-protocol.md](../standards/checkpoint-protocol.md) 为准。

在输出四阶段路线 + 波次排序后（若缺 T0，在此一并索要），Agent **必须停止、等待用户确认**，未获用户确认**不得写入下一步文件**（禁止自问自答）。停止时按 STOP 模板抛出以下确认话术：
<!-- @AI_GENERATED: end -->


> "这是按价值与数据就绪排序后的实施路线（四阶段）。请您确认：
> 1. 项目启动时间 T0 = [日期 / 待您提供]、节奏档位 = [集团级年度 / 单场景季度] 是否正确？（绝对日期据此换算）
> 2. 场景波次排序是否合理？尤其首批波次（阶段3）是否都数据就绪、缺数据的是否已正确排到阶段2 之后？
> 3. 总部统建 / 区域适配 / 现场执行的边界划分是否符合贵司组织实际？
>
> 确认后，我们将据此组装最终交付物（实施路线图 / Business Case 收尾）。"

**注意**：本步是工作流终步——确认后进入交付物组装（原 Phase 5）。在用户明确回复"确认"或给出修改之前，不允许擅自定稿正式排期。

## 单 agent / 多 agent 两种跑法

- **单 agent（基线，全平台可跑）**：当前 agent 顺序走完 7 步，过时间闸门，写 yaml + md，呈现终步检查点。
- **多 agent（探测到能力时）**：PL 派一个「Roadmap / Delivery Expert」做波次排序与排期；Partner 复核（节奏是否现实、缺数据场景是否被排太前、四阶段交付物是否可验收、建设边界是否清晰）。协调统一经 PL（hub-and-spoke），不依赖队友互发消息。

## 与上下游的衔接

- **上游**：步 10 提供技术架构（Ontology）（数据来源 / 本体三框 / Agent Skill / Agent 行动主体；其 agent、agent skill、数据接入作为四阶段建设波次的建设对象）；步 09 提供各场景价值量级与待确认数据；步 08 提供可行性与前置条件。

- **下游**：工作流收尾 → 交付物组装（原 Phase 5：按 `--format` 产出 md/html/pptx/docx/notion）与后续步骤建议（原 Phase 6）。
